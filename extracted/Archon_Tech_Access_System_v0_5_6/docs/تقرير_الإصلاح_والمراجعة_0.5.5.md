## 2. نتيجة تحليل سبب الخطأ

في `src/vba/modArchonReports.bas` من 0.5.4 وُجدت عبارتا `LEFT JOIN` تحتويان على شروط متعددة داخل `ON`:

1. `qryAT_BuildingCurrentOwners`
2. `qryAT_UnitDirectory`

وكان شرط الربط يتضمن مطابقة `BuildingID`، ثم شرط `StartDate<=Date()`، ثم شرطًا مركبًا `EndDate Is Null OR EndDate>=Date()`.

هذا هو الموضع البرمجي الذي يطابق رسالة Access 3296 «تعبير JOIN غير معتمد» بدرجة عالية. شروط التاريخ نفسها صحيحة من حيث المقصود، لكن وضعها داخل `ON` في هذين الربطين الخارجيين هو موضع التعارض المرجح مع محلل Access SQL/ACE.

لم أتعامل مع الأرقام المنسوخة من أسماء الصور على أنها أدلة مستقلة. وراجعت مسار الخطأ في المصدر: كان منشئ التقارير يلتقط الخطأ ويعيد `False`، ثم كانت الواجهة تنشئ خطأ عامًا باستخدام `vbObjectError + 690`، وبعد ذلك تعيد طبقات الواجهة والمثبت رفع الخطأ بمصادر عامة. لذلك فالرسائل اللاحقة كانت طبقات تغليف لفشل بناء الاستعلامات، لا دليلًا على ثلاثة أسباب مستقلة.

**حد الإثبات:** لا تتوفر بيئة Access/ACE في جلسة الإصلاح، لذلك لم أستطع تشغيل الاستعلام الأصلي داخل المحرك لإثبات رقم 3296 عمليًا. التشخيص مستند إلى نص الرسالة الذي زوّدتني به وإلى موضعي SQL الفعليين في حزمة 0.5.4. لذلك أسجل السبب على أنه السبب الجذري المرجح بقوة، لا نتيجة اختبار تشغيل فعلي.

## 3. الإصلاحات التي نُفذت

### أ. إصلاح JOIN مع حفظ منطق الملكية

أُضيف الاستعلام المحفوظ `qryAT_CurrentBuildingOwnership`، وفيه شروط التاريخ نفسها:

- `StartDate<=Date()`
- `EndDate Is Null OR EndDate>=Date()`

ثم عُدّل الاستعلامان المتأثران ليربطا `BuildingID` فقط مع هذا الاستعلام الوسيط، ويستمر ربط المالك بواسطة `OwnerID`.

لم تتغير الجداول أو الحقول أو تواريخ سريان الملكية أو طريقة عرض المباني والوحدات. ولم تُحذف أي بيانات أو علاقات أو نماذج.

### ب. التحقق من كل استعلام عند إنشائه

أصبح إجراء بناء التقارير يفتح كل `QueryDef` فور إنشائه بواسطة `OpenRecordset(dbOpenSnapshot)`. هذا يجعل Access/DAO يتحقق وقت التثبيت من صياغة الاستعلام والجداول والحقول والتعابير والاستعلامات السابقة التي يعتمد عليها، قبل الانتقال إلى إنشاء الواجهات.

إذا فشل الاستعلام، يضيف مسار الخطأ اسم `QueryDef` إلى `Err.Source`. وعند استبدال استعلام موجود، يحفظ الإجراء نص SQL السابق ويحاول استعادته إذا فشل إنشاء البديل أو فتحه. ولا يحاول حذف التعريف القديم إن لم ينجح حذفه أصلًا.

### ج. منع تغليف الخطأ الأصلي بخطأ عام

- استُبدل إطلاق `vbObjectError + 690` بعد فشل التقارير باستدعاء مباشر لمنشئ التقارير؛ الخطأ الأصلي ينتقل الآن إلى معالج الواجهة.
- تحفظ طبقة الواجهة `Err.Source` وتعرضه، ثم تعيد رفع الخطأ بالمصدر نفسه.
- تحفظ طبقة المثبت وواجهة الدخول عبر COM مصدر الخطأ الأصلي أيضًا.

النتيجة المقصودة أن يظهر اسم الاستعلام الذي فشل ورقم/وصف الخطأ الأصلي بدل أن يُستبدل بخطأ عام عن إنشاء الواجهات أو التثبيت.

## 6. الاختبارات التي لم تُنفذ

بيئة الإصلاح الحالية Linux ولا تحتوي Microsoft Access أو DAO/ACE أو Windows COM أو Windows PowerShell. لذلك لم أتمكن من تنفيذ:

1. استيراد وحدات VBA إلى Access أو `Debug > Compile`.
2. تشغيل `CreateQueryDef` و`OpenRecordset` فعليًا داخل ACE. كود التحقق أُضيف للحزمة ليجري هذا الاختبار عند التثبيت على Access، لكنه لم يُنفذ في بيئة إعداد الحزمة.
3. إنشاء ملفات FE/BE الفعلية، أو التحقق من إنشاء النماذج والتقارير وفتحها والطباعة/PDF.
4. تشغيل Parser الخاص بـ Windows PowerShell.
5. تشغيل حالات القبول الستين أو اختبار النسخ الاحتياطي والاستعادة على Access فعلي.

لم أعتبر وجود فحص ساكن بديلًا عن هذه الاختبارات، ولم أصف VBA Compile أو تشغيل Access بأنه ناجح.
